## Журнал ресерча — использованные команды и источники

Парсинг статей (ocrc → локальный dots.mocr-сервис, markdown + layout JSON по
страницам; см. `AGENTS.md`). Финальная рабочая схема: сначала скачать PDF
локально (DNS до arxiv.org из шелла флаки), затем парсить локальный файл.
Когда stdout — пайп, ocrc стримит бандл (.zip) в stdout и игнорирует `--out`,
поэтому stdout перенаправляется в zip-файл, который потом распаковывается:

```bash
mkdir -p /tmp/ocrc_md/pdf && cd /tmp/ocrc_md/pdf
for spec in "deepseek_v3 2412.19437" "deepseek_r1 2501.12948" \
            "qwen25 2412.15115" "qwen3 2505.09388" "kimi_k2 2507.20534" \
            "kimi_k15 2501.12599" "glm45 2508.06471" "llama3 2407.21783"; do
  set -- $spec
  for attempt in 1 2 3 4 5; do   # DNS флаки -> ретраи
    curl -fsSL --connect-timeout 15 --retry 3 --retry-all-errors \
      -o "$1.pdf" "https://arxiv.org/pdf/$2" && break
    sleep 5
  done
done

cd /tmp/ocrc_md
ocrc parse pdf/<name>.pdf --out <name> --quiet > <name>.zip 2> <name>.log
unzip -o -q -d <name> <name>.zip        # pipe-режим: бандл приезжает в stdout
```

Каждый парс проверен на полноту страниц (`meta.json.pages_done` против набора
файлов `layout/*page_N.json`): deepseek_v4 58 стр., deepseek_v3 53,
deepseek_r1 86, llama3 92, qwen25 26, qwen3 35, kimi_k2 32, kimi_k15 25,
glm45 26 — ноль пропущенных страниц, ноль продублированных диапазонов.

История, которую стоит сохранить (почему `parsing error` — не вина движка):
в первом заходе DeepSeek-R1 воспроизводимо умирал после 14-й страницы любой
задачи, а Llama 3 не парсился вообще. Корневая причина — ложноположительная
защита (`is_page_safe_to_render` в `src/dots_mocr/utils/doc_utils.py`
репозитория ocr-сервиса), отвергавшая страницы, у которых *встроенные*
изображения больше 30M пикселей, — хотя MuPDF растеризует страницу в размере,
ограниченном матрицей рендера, и никогда не распаковывает встроенное
изображение в нативном разрешении (замерено: стр. 16 PDF R1 со встроенной
картинкой 11881×7646 = 91M px рендерится за 0.07 с при пиковом RSS 70 MB).
Исправлено апстримом в RepnikovPavel/ocr PR #17 («render pages with
oversized embedded images instead of rejecting them»); после фикса все девять
статей распарсены как одиночные полнодокументные задачи — без `--split` и без
ошибок.

## 0. Термины

- **BOQ / EOQ** — *begin/end of question*: маркерные токены, обрамляющие
  спан инструкции. Дефолты переиспользуют имена ChatML: BOQ =
  `<|im_start|>`, EOQ = `<|im_end|>`.
- **EOA** — *end of answer*: маркер, добавляемый после ответа. В этом
  пайплайне это должен быть `<|endoftext|>` (аналог EOS); дефолт же
  Rust-бинарника — `<|box_end|>` — см. §6.
- **`<|PAD|>`** — токен паддинга, id 0. Сейчас не используется: сэмплер его
  не пишет (каждый сэмпл хранится со своей естественной длиной; паддинг,
  если он есть, происходит в тренере, которого в этом репо нет).
- **condition-тег vs condition-токен** — *тег* — это строка в очищенных
  данных (`"condition": "noisy,cot"` в JSONL/parquet-строке). При
  токенизации каждый тег отображается на выделенный *токен* словаря:
  `direct → <|direct|>` (id 1), `cot → <|cot|>` (2), `noisy → <|noisy|>` (3),
  `synth → <|synth|>` (4). Эти id — **не** магические константы: это
  позиции этих имён в списке `--special-tokens` в
  `train_tokenizer.rs:52-68`; бинарник токенизации обратно резолвит их по
  имени через `token_to_id`.
- **task (задача)** — один токенизированный исходный файл = один выходной
  подкаталог (`<safe_name>`, разделители путей заменены на `__`). Для
  clustered-датасетов один датасет = много задач (`flan__cot__*` и т.п.);
  отчёт группирует по части имени до `__` («категория»).
- **эпоха** — один заранее посчитанный проход по миксу: набор
  index-массивов, выбирающих, какие строки и в каком порядке идут в
  обучение. Что копируется, а что индексируется — см. §2.
- **DDP / rank / shard** — Distributed Data Parallel: каждая нода гонит ту
  же модель и потребляет свой *шард* (кусок) каждой эпохи; *rank* —
  глобальный номер процесса. Код шардирования живёт в тренере, в этом репо
  его нет.
- **ФС** — файловая система. «Общая ФС» — сетевая файловая система, видная
  всем нодам (NFS/Lustre/…); этот пайплайн сознательно не требует её во
  время обучения.
- **`/dev/shm`** — RAM-диск (tmpfs) в Linux. Писать туда сэмплированный
  датасет = держать его в памяти, но с файловым интерфейсом.
- **mmap** — отображение файла в память: чтения обслуживаются из page
  cache / RAM вместо явного I/O.

## 1. Что реально пишет стадия токенизации

На каждую очищенную строку (`tokenizer/src/main.rs:231-255`):

```
instruction-спан: BOQ + <condition-токены...> + encode(instruction) + EOQ
response-спан:    encode(response) + EOA
```

- `inst_len` включает BOQ, condition-токены и EOQ; `resp_len` включает
  завершающий EOA. Это важно для всех вычислений длин ниже по конвейеру
  (см. §5).
- Поскольку теги — настоящие токены внутри instruction-спана, обучаемая
  модель буквально кондиционируется на тегах микса: подал в промпт
  `<|cot|>` вместо `<|direct|>` — попросил другое поведение.
- На каждый исходный файл: `tokens.npy` (**u32** id'ы, склеенные) + четыре
  **u64**-массива границ + `metadata.json`, содержащий только
  `{source_mtime, source_size}`. Повторный запуск токенизатора пропускает
  файлы с неизменившимися mtime+size и удаляет выходные каталоги, чей
  источник исчез («prune orphans», `main.rs:151-162`) — это и есть вся
  инкрементальность.
- `tokenizer_info.json` в корне выхода фиксирует строки маркеров, маппинг
  condition-тегов и размер словаря; `sample_tokenized.py` читает оттуда
  vocab size.

## 2. Что делает стадия сэмплинга — данные копируются один раз, эпохи — это индексы

Основной поток `sample_tokenized.py`:

1. Сканирует `tokenized_path/<task>/`, грузит четыре index-массива на задачу,
   сопоставляет имя задачи с **префиксами из `prefix_config.yaml` по порядку,
   первое совпадение побеждает** (`:267-273`). Несматченные задачи молча
   получают дефолт: без капа, `truncate`, `repeat=1`.
2. `concat_tokens` (`:86-131`): копирует **все** `tokens.npy` всех задач
   **ровно один раз** в один большой массив `output_path/tokens.npy`,
   записывая каждой задаче её `mmap_base_offset`. dtype — uint8/uint16 по
   размеру словаря (65k → uint16; баг с границей тут уже исправлен, см.
   `tokenizer/docs/gotchas.md`). Конкатенация идёт **до** фильтрации
   (`:285-289`), поэтому массив содержит весь корпус, включая строки,
   которые сейчас будут выброшены, — фильтрация переписывает только
   index-массивы, токены не трогает.
3. `truncate_and_filter` по каждой задаче (§5).
4. Генерация эпох (`:292-346`): один Philox-генератор с сидом `seed`. На
   эпоху, на задачу: `min(max_per_file, n_rows) * repeat` строк, взятых по
   перестановке задачи (перетасовывается при исчерпании → сэмплинг без
   возврата внутри прохода), спаны переводятся в глобальные смещения, одна
   глобальная перестановка всего эпочного буфера, затем пишется
   `epoch_N/{inst_start,inst_len,resp_start,resp_len}.npy` (**int64**).
   В `metadata.json` пишутся `max_seq_len` и сумма токенов на эпоху.
5. Markdown-отчёт о покрытии в stdout.

**Нет, данные под каждую эпоху не копируются.** Токены существуют ровно в
одном месте (конкатенированный массив); эпоха — это *только* четыре
int64-массива индексов: 32 байта на строку на эпоху против ~600 байт
реальных токенов на среднюю строку (296.5 токенов × 2 байта). Десять эпох
индексов стоят порядка десятков ГиБ, а не десять копий 330-ГиБ корпуса.
Эпохи строятся заранее (а не на лету), чтобы каждая нода загрузила
идентичное, уже перемешанное расписание детерминированно, а старт тренера
сводился к mmap.

**Зачем нужны `max_per_file` / `repeat`.** Без капов одна эпоха ≈ сырой микс
корпуса: один FLAN — это 78% всех токенов, а маленькие качественные сеты
растворились бы в шуме. YAML перебалансирует микс внутри эпохи:

- `max_per_file: N` — не больше N строк из *этого файла* за эпоху (кап на
  файл; clustered-датасет состоит из многих файлов). Например, `dmmath__`
  ограничен 100k строк/файл/эпоху, `flan__` — 5k, `openmathinstruct2__` —
  2M.
- `repeat: R` — каждая оставленная строка эмитится R раз за эпоху
  (апсэмплинг маленьких HQ-сетов: семейство Platypus, gsm8k, math_train и
  т.д. используют `repeat: 10`).
- Эффективное число строк на эпоху на файл: `min(cap, n_rows) * repeat`.

Строки за капом не теряются — они заходят в следующие эпохи через свежие
перестановки, поэтому многоэпочное обучение всё равно покрывает корпус.

## 3. Логика авторов — почему всё устроено именно так

- **Токенизировать ровно один раз.** Границы сохраняются, а не вычисляются
  заново: тренер может маскировать loss по response-спану, а сэмплер —
  считать длины индексированием массива. Per-file раскладка делает
  токенизатор инкрементальным.
- **Condition-теги как токены.** Семантика микса доживает до самого потока
  токенов и адресуется во время обучения/инференса.
- **Детерминированные материализованные эпохи.** Philox с фиксированным
  сидом выдаёт одинаковые байты на любой машине — мультинодовый контракт:
  каждая нода запускает тот же скрипт в свой `/dev/shm`, все ноды получают
  идентичный датасет, DDP-ранги шардируют эпохи консистентно без всякой
  координации и без общей ФС на время обучения.
- **`/dev/shm` — это суть, а не причуда.** Тренер делает random access в
  `tokens.npy` через эпочные индексы; RAM превращает даталоадер в арифметику
  указателей. Цена: корпус должен помещаться в RAM ноды — 176.1B токенов ×
  uint16 ≈ 330 ГиБ плюс индексы.
- **Управление миксом живёт в YAML.** Капы/repeat перебалансируют эпоху без
  правок кода; перестановки дают полное покрытие за много эпох.

## 4. Мультинод → одна нода: есть ли зашитое смещение?

Короткий ответ: стохастического смещения нет, но есть два структурных
допущения.

- Данные **побайтово одинаковы на всех нодах** по построению (тот же сид,
  те же перестановки). Одна нода ничего не меняет в том, что модель видит за
  эпоху, — более того, пропорции микса per-epoch выполняются даже *точнее*,
  потому что одна нода потребляет эпохи целиком, а не шардирует их на N нод
  (внутри одного шарда пропорции с капами держатся лишь приближённо).
- Подлинное мультинодовое допущение — **«каждая нода может держать весь
  корпус в RAM»**. На одной ноде это требование сохраняется: закладывайте
  ≥ ~350 ГиБ под `/dev/shm` (или укажите `output_path` на NVMe-каталог и
  примите чтения через page cache).
- Единственная по-настоящему зависящая от числа нод часть — **как тренер
  шардирует `epoch_N/` по рангам** — этого кода в репозитории нет. Проверьте
  нарезку эпочных массивов по рангам в тренере (stride или сплошные куски),
  прежде чем считать, что семантика сэмплинга из README переносится как
  есть.
- Ничто в сэмплере не знает про число нод, world size или rank. Опасение
  «мультинодового bias» сводится к: те же данные, тот же порядок, плюс
  требование по RAM.

## 5. Процедура обрезки под контекст — подробно

`truncate_and_filter` (`sample_tokenized.py:68-83`), при
`context_size = 4097` (4096 + 1 на AR-сдвиг):

```python
allowed_resp = context_size - min(inst_len, context_size)
# режим truncate (дефолт):
оставить если resp_len >= min_resp_length и allowed_resp >= 1
resp_len = min(resp_len, allowed_resp)
# режим drop:
оставить если resp_len >= min_resp_length и resp_len <= allowed_resp
```

- **Инструкция никогда не урезается.** Строки, у которых одна *инструкция*
  достигает контекста, **выбрасываются целиком** в обоих режимах
  (`min(inst_len, ctx)` упирается в ctx → `allowed_resp = 0` → не проходит
  `allowed_resp >= 1`).
- **Режется только ответ, и с хвоста.** Урезанная строка сохраняет первые
  `allowed_resp` токенов ответа.
- **Урезанные строки теряют EOA.** EOA — это *последний* токен
  response-спана; усечение `resp_len` его срезает. Модель обучается на
  таргетах, которые обрываются посреди мысли без маркера конца, — прямой
  удар по stop-поведению. Доля строк без EOA равна доле урезанных.
- **Срез происходит на произвольной границе токена** — посреди слова,
  посреди LaTeX, посреди кода. Id'ы валидны, так что ничто ниже по конвейеру
  не упадёт; ущерб чисто статистический.
- **Смещение систематическое.** Обрезка бьёт по длинным ответам —
  непропорционально по длинно-CoT сетам (numinamath, acereason,
  openthoughts2, textbookreasoning, principia), — тогда как короткоответные
  (dmmath, sudoku, gsm8k) не затронуты. Ручка «сколько явного рассуждения
  учит микс» тихо выкручивается вниз ровно на длинном, сложном конце.
- **Ваши исходные данные НЕ портятся.** Усечение переписывает только
  index-массивы в памяти; per-file `tokens.npy` и конкатенированный массив
  не трогаются. Повторный запуск сэмплера с другими настройками полностью
  всё восстанавливает.
- **Краевой случай:** `allowed_resp >= 1` допускает строки, чей урезанный
  ответ — один токен (без EOA): таргет в один токен, который почти ничему не
  учит.
- **Вариативность длин** ниже капа сохраняется (здесь нет паддинга/паковки);
  теряется только хвост за 4097.

## 6. Заложенные в код бомбы — что делает каждая и чем грозит

По каждому пункту: механизм, сценарий отказа и варианты решения.

### 6.1 Тихая потеря строк на стадии токенизации

`main.rs:232-233` оборачивает кодирование в
`if let Ok(...) = tok.encode_fast(...)`. Строка, которая не закодировалась,
пропускается — без счётчика и без строчки в логе. Ошибки уровня файла
печатаются, но не роняют прогон (`main.rs:186-189`), и прогресс-бар
инкрементируется в любом случае.

- **Чем грозит:** токенизированный корпус может молча содержать меньше строк,
  чем очищенный; ничто ниже по конвейеру не сверяет счётчики, так что вы
  заметите это разве что по загадочно меньшему итогу токенов.
- **Варианты:** (a) принять — ошибки кодирования на уже провалидированном
  UTF-8 редки; (b) допатчить `process_row`, чтобы он считал пропуски по
  файлам и печатал сводку (маленькое изменение, высокая диагностическая
  ценность); (c) как минимум один раз сверить число строк на файл
  (`wc -l` / метаданные parquet) с `len(inst_len.npy)`.

### 6.2 Обратная политика при *обучении* токенизатора: паника на первом битом файле

`train_tokenizer.rs:134` вызывает `read_any_stream(...).unwrap()` внутри
rayon-замыкания — один битый/обрезанный исходный файл роняет весь прогон
обучения (в итеративном тренере это хотя бы поднимается с чекпоинтов).

- **Чем грозит:** стадия токенизации молча выбрасывает строки, стадия
  обучения словаря умирает на той же категории проблем. Несогласованные
  политики отказа — поведение одной стадии не предсказуемо по другой.
- **Варианты:** оставить как есть (громкое падение при обучении словаря —
  это скорее хорошо: вы *хотите* знать); только не «выравнивайте» политики,
  делая обучение молчаливым.

### 6.3 Захардкоженные дефолты маркеров, указывающие на чужие токены

`main.rs:37-46`: дефолты `--boq/--eoq/--eoa/--conditions` рассчитаны на
стоковый токенизатор Qwen3, где **нет** выделенных condition-токенов, —
поэтому `direct/cot/noisy/synth` по дефолту мапятся на *vision*-токены Qwen
(`<|object_ref_start|>`, `<|object_ref_end|>`, `<|quad_start|>`,
`<|quad_end|>`), а EOA по дефолту — `<|box_end|>`. В нашем обученном
токенизаторе выделенные токены есть, но ничто не предупредит, если вы
забудете флаги.

- **Чем грозит:** корпус, где каждый condition-маркер — vision-loc токен, а
  каждый ответ заканчивается `<|box_end|>` вместо `<|endoftext|>` —
  семантически неверное кондиционирование и стоп-токен, который тренер может
  не считать EOS. Полностью молча; что реально использовалось, записано
  только в `tokenizer_info.json`.
- **Варианты:** (a) проверить `tokenizer_info.json` артефакта, из которого
  будете сэмплировать (поля condition_mapping и eoa) — один `cat`, сделайте
  сейчас; (b) поменять дефолты в `main.rs` на выделенные токены, чтобы
  безопасный путь был дефолтным; (c) добавить проверку на старте: если в
  токенизаторе есть `<|direct|>`, требовать явный `--conditions`.

### 6.4 Id спец-токенов позиционные

Id 0–30 присваиваются по порядку списка `--special-tokens` в
`train_tokenizer.rs:52-68`. Переобучение словаря с переставленным/дополненным
списком сдвигает все id.

- **Чем грозит:** ломается всё, что ключуется по id, а не по имени: старые
  токенизированные датасеты, обученные чекпоинты (строки эмбеддинга),
  внешние eval-обвязки. Внутри этого репо резолв идёт по имени
  (`token_to_id`), так что *свежий* сквозной прогон самосогласован; смешение
  артефактов разных версий словаря — нет.
- **Варианты:** считать `tokenizer.json` + токенизированный корпус +
  чекпоинт единым версионируемым бандлом; список никогда не переупорядочивать,
  только дополнять в конец.

### 6.5 u32-токены на диске против uint16 в сэмплере

Токенизатор пишет `tokens.npy` как **u32** (`main.rs:224`, `Vec<u32>`);
сэмплер перепаковывает в **uint16** для словаря 65536
(`sample_tokenized.py:100-118`, исправленная граница).

- **Чем грозит:** промежуточный токенизированный корпус занимает 4
  байта/токен (~700 ГиБ на 176B токенов) там, где хватило бы 2, — вдвое
  больше диска и вдвое больше трафика чтения на конкатенации. Это не вопрос
  корректности (u32 — безопасный дефолт для произвольных словарей).
- **Варианты:** (a) принять — диск дешёвый, а финальный артефакт и так
  uint16; (b) писать uint16 прямо из токенизатора, когда
  `vocab_size - 1 <= u16::MAX` (здесь max id = 65535 влезает впритык) —
  вдвое меньше промежуточный след, ценой небольшого патча и повторной
  токенизации.

### 6.6 Глобальная связность RNG

Один Philox-поток потребляется в отсортированном порядке задач;
добавление/удаление/переименование датасета меняет перестановки **всех**
датасетов.

- **Чем грозит:** нельзя A/B-протестировать добавление одного датасета,
  зафиксировав остальное расписание; «тот же сид» воспроизводит только тот
  же самый список задач.
- **Варианты:** принять (важен микс эпохи, а не порядок внутри задачи) или
  пересевать RNG на задачу хэшем имени задачи, если нужны стабильные
  per-task выборки.

### 6.7 Молчаливый дефолт для несматченных префиксов

Задача, чьё имя не совпало ни с одним префиксом из `prefix_config.yaml`,
получает `PrefixConfig()` — без капа, truncate, repeat 1 — без всякого
предупреждения.

- **Чем грозит:** опечатка в префиксе молча отключает задуманный кап/repeat,
  и соответствующий датасет либо затапливает микс, либо перестаёт
  апсэмплиться.
- **Варианты:** один раз прогнать сэмплер и прочитать отчёт о покрытии —
  несматченные датасеты видны по полному числу строк; либо допатчить
  загрузчик, чтобы он печатал сматченный префикс по каждой задаче.

### 6.8 Аналитика слепа к усечению и выбросам

`Stats.cov_rows_truncated` объявлен (`sample_tokenized.py:146`), но нигде не
заполняется; отчёт показывает покрытие, а не то, сколько строк выброшено или
урезано в `truncate_and_filter`.

- **Чем грозит:** самая разрушительная ручка пайплайна (§5) невидима в
  `show_analytics.md`; можно неделями обучаться на корпусе с ампутированным
  длинно-CoT хвостом, и ни одно число вам об этом не скажет.
- **Варианты:** заполнить `cov_rows_truncated` + счётчик выброшенных строк в
  `truncate_and_filter` (маски там уже в руках — тривиальный патч); либо
  посчитать статистику drop/truncate офлайн только по четырём
  index-массивам (данные токенов не нужны).

## 7. Рекомендации перед обучением на одной ноде

1. **Измерьте, не гадайте.** По каждому датасету: строк выброшено
   (инструкция ≥ 4097), строк урезано, перцентили длин ответов относительно
   4097 — только по index-массивам или через патч из §6.8.
2. **Предпочитайте `drop` вместо `truncate` для HQ-сетов с рассуждениями.**
   Отсутствующее решение ничему не учит; решение, обрезанное посреди
   доказательства *без EOA*, учит «обрываться посреди мысли».
   `long_context` задаётся по префиксам — это правка YAML, например `drop`
   для numinamath/acereason/openthoughts2.
3. **Если усечение оставляете — подумайте о возврате EOA** урезанным строкам
   (перезаписать последний оставленный токен ответа на EOA при конкатенации
   или выдавать маску «has_eoa»). В коде авторов этого нет — сознательный
   компромисс качества, который стоит пересмотреть.
4. **Проверьте `tokenizer_info.json` артефакта** (§6.3): выделенные
   condition-токены и `<|endoftext|>` в роли EOA, а не дефолты из
   Qwen-vision.
5. **Бюджет RAM:** `/dev/shm` ≥ ~350 ГиБ под полный корпус 176B токенов в
   uint16 плюс эпочные буферы (§2). На одной ноде без конкатенированного
   массива не обойтись, если только не переписать сэмплер на per-task файлы
   с индексами вида (task, offset).
6. **Сохраните workflow с фиксированным сидом.** На одной ноде это ничего не
   стоит и сохраняет сопоставимость прогонов с сетапом авторов.


## 8. Proposal: честный дизайн спец-токенов (у нас полный контроль)

Весь пайплайн под нашим контролем, а переобучение токенизатора дешёвое
(~1 час), поэтому правильный ход — не обходить костыли авторов, а заменить
их. Ниже — целевой дизайн и план миграции; ничто здесь не требует сохранять
хоть что-то от текущего блока спец-токенов.

### 8.0 Что на самом деле не так (рекап)

- 31 спец-токен, из которых пайплайн использует ~7. Остальное — скопированный
  блок спец-токенов Qwen3 (имена vision/agent/FIM). В наш поток токенов они
  попасть не могут: `main.rs` пушит только id'ы BOQ/condition/EOQ/EOA явно, а
  из-за `set_encode_special_tokens(true)` токенизатор *разбивает* строки
  спец-токенов в тексте корпуса как обычный текст, а не эмитит их id
  (tokenizers 0.22.2, `added_vocabulary.rs:163-164`: «Whether or not special
  tokens should be splitted when encoding. This is equivalent to ignoring
  them»). То есть багаж — это мёртвый словарь, а не угроза данным, — мёртвый
  словарь, который стоит строк эмбеддинга и, что хуже, спровоцировал костыль
  с алиасингом на vision-токены ниже.
- CLI-дефолты алиасят `direct/cot/noisy/synth` на *vision*-токены Qwen, а
  EOA — на `<|box_end|>` — молча неверная семантика (§6.3).
- Condition-токены эмитятся **внутри каждой обучающей инструкции**, т.е.
  входной контракт модели содержит захардкоженный кусок промпта:
  произвольный промпт на инференсе вне распределения, если вы сами не
  подставите магические токены.

### 8.1 Целевой словарь: минимальный честный блок спец-токенов

Рецепт (без вариантов — это финальный список; обоснование по каждому токену
в §10 после кросс-вендорного обзора):

```text
0 <|PAD|>            паддинг (на стороне тренера; дата-пайплайн его не эмитит)
1 <|begin_of_text|>  BOS — первый токен каждой обучающей последовательности
2 <|endoftext|>     EOS — завершает ответ (единственный стоп-токен)
3 <|im_start|>       BOQ — открывает блок инструкции
4 <|im_end|>         EOQ — закрывает блок инструкции
5 <|think|>          открывает блок рассуждения (cot-строки)
6 </think|>          закрывает блок рассуждения; дальше идёт ответ
```

Больше ничего. Каждый токен несёт реальную, задокументированную функцию; ни
алиасинга, ни мёртвого груза. Правила, чтобы это не расслоилось со временем:

- id позиционные — **только дополнять в конец**, никогда не переупорядочивать
  (§6.4);
- имя говорит, что токен *делает*, а не какое семейство моделей вдохновило;
- `vocab_size` остаётся 65536: меньше спец-токенов — просто несколько
  свободных слотов под BPE-мерджи (выигрыш в компрессии на уровне
  округления).

**«Почему есть токен конца, но нет токена старта работы модели?»** — вопрос
отвечает сам себе, стоит посмотреть на текущую раскладку: каждая обучающая
последовательность уже начинается с фиксированного маркера (`<|im_start|>`),
так что BOQ всё это время был де-факто токеном старта; отдельный BOS перед
ним для чисто-QA корпуса избыточен (это ровно дизайн Qwen3: `bos_token:
null`, `add_bos_token: false`, eos = `<|im_end|>`). Тем не менее в рецепт
включён явный `<|begin_of_text|>`, потому что DeepSeek-V3/R1/V4
(`<｜begin▁of▁sentence｜>`), Llama 3 (`<|begin_of_text|>`) и Kimi K2 (`[BOS]`)
все его несут: это стоит одну строку эмбеддинга, даёт генерации
однозначный якорный токен и оставляет дверь открытой для не-QA
предобучающих данных, где никакого `im_start` нет. Раскладка
последовательности: `BOS BOQ inst EOQ [think … /think] ответ EOS`.

**Никакого маркера `<|answer|>`.** Эталонные thinking-модели
(DeepSeek-R1/V4, Qwen3) его не используют: финальный ответ — это просто
текст после закрывающего think-тега. Отдельный токен ответа добавил бы
третий уровень вложенности без выигрыша; оценка качества извлекает спан
после `</think|>`.

### 8.2 Целевой поток токенов: без кондиционирования на метаданные микса

```text
cot-строки:    <|begin_of_text|> <|im_start|> инструкция <|im_end|> <|think|> рассуждение </think|> ответ <|endoftext|>
direct-строки: <|begin_of_text|> <|im_start|> инструкция <|im_end|> ответ <|endoftext|>
```

- **Никаких condition-токенов в потоке.** `direct/cot/noisy/synth` — это
  метаданные датасета: они живут в колонке `condition` очищенных данных
  (для аналитики и фильтрации) и в `prefix_config.yaml` (для управления
  миксом через префиксы файлов). Ни одному из этих потребителей не нужно,
  чтобы модель их видела.
- Различие cot/direct выражено так, как его выражают обычные
  thinking-модели: рассуждение в think-тегах, финальный ответ после них,
  один EOS. На инференсе модель по умолчанию думает, а к прямому ответу её
  можно подтолкнуть префиллом пустого `<|think|></think|>`. Произвольные
  промпты in-distribution: `<|im_start|>промпт<|im_end|>` → генерация до
  `<|endoftext|>`.
- Маскирование loss не страдает: тренер по-прежнему получает спаны
  инструкции/ответа (просто в response-спане теперь внутри лежат
  think-теги).

Честная цена: большинство cleaning-скриптов пишут в `response` полное
решение, а короткий ответ дают *отдельной* `direct`-строкой. Чтобы собрать
`рассуждение | ответ` для cot-строк, переиспользуйте парные direct-строки
(джойн по тексту инструкции — чисто работает для math_train/numinamath/
omnimath, где есть явные короткие ответы) или оберните всё решение в
think-теги и ничего после них не пишите (слабее паттерн «ответ после
think»). Это единственный шаг, который трогает per-dataset логику.

### 8.3 План миграции

1. **Словарь**: сократить список `--special-tokens` в
   `train_tokenizer.rs:52-68` (и в итеративном тренере) до §8.1,
   переобучить (~1 час; итеративный тренер чекпоинтится, так что прогон
   перезапускаем). В остальном обучение BPE не меняется.
2. **Стадия токенизации** (`main.rs`): удалить эмиссию condition-токенов из
   `process_row`; сделать EOA по дефолту `<|endoftext|>`; удалить флаг
   `--conditions` и путь алиасинга на vision-токены целиком (удалённый код
   не может быть молча неверным). Если делаете think-формат из §8.2 —
   оборачивайте cot-ответы здесь же (строка condition и так приходит в
   `process_row`).
3. **Перетокенизировать корпус** в свежий выходной каталог (инкрементальная
   механика mtime/size для чистой пересборки не нужна; старый артефакт
   держите, пока новый не проверен).
4. **Перезапустить сэмплер** — код не меняется; он читает спаны и размер
   словаря, а не имена маркеров.
5. **Проверить**: `tokenizer_info.json` показывает новый маппинг; число
   строк на файл совпадает с очищенным корпусом (проверка из §6.1);
   статистика drop/truncate по §7.1 — до любого обучения.

### 8.4 Чем это стоит и что ломает

- Стоит: ~1 час переобучения словаря + одна полная перетокенизация + один
  прогон сэмплера.
- Ломает (намеренно): сопоставимость со словарём/артефактами авторов —
  заметки о паритете в `tokenizer/docs/gotchas.md` (99.8% пересечения
  словаря, bug-for-bug воспроизведение i32-переполнения) перестают
  применяться, как только вы меняете список спец-токенов или чините
  переполнение. Если когда-нибудь понадобится воспроизвести их числа —
  держите их артефакт замороженным; иначе отпустите.
- НЕ ломает: cleaning-пайплайн, сэмплер, формат эпох/индексов, контракт со
  стороной обучения (спаны + max_seq_len + uint16).

### 8.5 Итог для решения

Формат авторов — это ярлык «демо ко дедлайну», а не ограничение.
Рекомендуемое конечное состояние: словарь §8.1 + поток §8.2 + политика
усечения из §7. Каждый пункт — независимое, обратимое изменение; вместе они
убирают все пути с молча-неверной семантикой, найденные в §6.

## 9. Покрывает ли один стандартный формат все 24 датасета без просадок качества?

Вопрос: влезает ли каждый датасет из `scripts/docs/README.md` в формат из
§8 (`BOQ inst EOQ [<|think|> рассуждение </|think|> ответ] EOA`, без
condition-токенов), или какие-то строки что-то теряют при таком принуждении?

Датасеты раскладываются на четыре формы:

1. **Рассуждение + извлекаемый короткий ответ** — math_train (`\boxed{}`),
   numinamath (поле `answer`, не-proof строки), omnimath, scibench,
   scienceqa (обоснование + буква), ampsmathematica, gsm8k (`####`). Эти
   ложатся чисто: решение → think-блок, короткий ответ → ответ после think.
   Ничего не теряется; формат даже *добавляет* структуру, которой у
   текущего плоского `response` нет.
2. **Трасса рассуждения без отделяемого ответа** — acereason и
   openthoughts2 (R1-подобные дистиллированные трассы, ответ внутри
   трассы), principia (синтетическая STEM-зарядка), textbookreasoning,
   natural_reasoning, webinstruct_verified, amps_khan (цепочки подсказок).
   Варианты: обернуть весь ответ в think-теги (позиция ответа остаётся
   пустой) или прогнать дешёвую экстракцию. В любом случае ничего не
   *теряется* — худший случай: паттерн «ответ после think» для этих строк
   отсутствует, и это ровно то, как законно выглядят proof-строки
   numinamath.
3. **Прямые ответы** — dmmath, sudoku_extreme, gsm8k-direct, MCQ-сеты
   (openbookqa, reclor, scienceqa-direct, arb-law), theoremqa, tasksource,
   flan-direct, no_robots, synth-direct. Тривиально: `BOQ inst EOQ ответ
   EOA`. Без think-блока — соответствует стандартному поведению
   thinking-моделей в режиме без размышлений.
4. **FLAN cot / synth cot подмножества** — CoT-текст есть, но без помеченного
   финального ответа; обработка как у группы 2.

Риски на уровне формата и их размер:

- **Оверхед маркеров на крошечных строках.** Строки dmmath в среднем ~40
  токенов; рамка из 4 токенов (BOQ/EOQ/EOA + think-теги, когда есть) уже
  есть и в текущем пайплайне (он тоже эмитит BOQ/conditions/EOQ/EOA), так
  что изменение ±0–2 токена на строку. Оптимизировать нечего.
- **Потеря рычага condition-токенов.** Заменяется рычагом think-формата
  (think vs пустой think) плюс управлением миксом на уровне префиксов —
  см. §8.2. Единственная по-настоящему теряемая способность — «генерировать
  с приором *noisy*», и у неё нет мыслимого применения.
- **HRM-специфичная структура.** Спаны inst/resp выживают без изменений
  (response-спан просто содержит think-теги внутри), так что контракт
  спанов/маскирования loss не меняется.
- **Оценка качества.** Деконтаминация и привязка бенчмарков
  (`scripts/docs/evaluation.md`) от формата не зависят.

Вердикт: да — один стандартный формат покрывает все 24 датасета; единственный
реальный рабочий пункт — экстракция ответа для группы 2, и её запасной
вариант (обернуть весь ответ в think, без отдельного ответа) не стоит данных
и совпадает с тем, как выглядят proof-строки.

## 10. Кросс-вендорный обзор: как большие команды устраивают токенизаторы и спец-токены

Источники: девять распарсенных статей из журнала ресерча (страницы —
страницы arXiv PDF, 1-based) плюс raw-файлы `tokenizer_config.json` по
ссылкам оттуда. Факты из HF-конфигов даны без номеров страниц — конфиг сам
является источником. «В статье нет» ниже означает: проверено полнотекстово
по распарсенному markdown, а не «не проверяли».

### DeepSeek (V3, R1, V4)

- BBPE, словарь 128K; претокенизатор «вводит токены, склеивающие пунктуацию
  и переводы строк»; против возникающего token-boundary bias часть таких
  склеенных токенов при обучении случайно разбивают (DeepSeek-V3, §4.1, PDF
  с. 22).
- FIM — часть предобучения: фреймворк PSM, разметка последовательности
  `<|fim_begin|>f_pre<|fim_hole|>f_suf<|fim_end|>f_middle<|eos_token|>`,
  применяется с долей 0.1 (DeepSeek-V3, §4.1, PDF с. 22; подчёркивания в
  markdown были заэкранированы бэкслешами, написания литеральные).
- Пакинг: V3 пакует документы, «но не использует cross-sample attention
  masking» (§4.1, PDF с. 22); V4 тоже пакует и *добавляет* маскирование на
  уровне сэмплов (DeepSeek-V4, §4.1, PDF с. 24).
- V4 сохраняет токенизатор V3 со словарём 128K, добавляя лишь «несколько
  спец-токенов для конструирования контекста» (DeepSeek-V4, §4.1, PDF
  с. 24).
- BOS `<｜begin▁of▁sentence｜>`, EOS `<｜end▁of▁sentence｜>`, pad = EOS; роли
  чата `<｜User｜>` / `<｜Assistant｜>` (HF: tokenizer_config.json
  DeepSeek-V3). Статьи эти литералы не печатают — факты только из конфига.
- R1 (статья): RL-шаблон R1-Zero определяет `<think>...</think>` и
  `<answer>...</answer>` как **обычные текстовые теги**, а format-награда
  контролирует только think-теги (DeepSeek-R1, Table 1 PDF с. 3, §2.2 PDF
  с. 4). Документации токенизатора в статье R1 нет вообще (проверено).
- HF-шаблон чата R1 завершает ход ассистента EOS и префиллит генерацию
  `<｜Assistant｜><think>\n` — в R1 think-теги это литеральный текст шаблона
  (HF: tokenizer_config.json DeepSeek-R1).
- V4 делает `<think></think>` *выделенной* парой тегов, разграничивающей
  режимы рассуждения (DeepSeek-V4, §5.1.1, Table 2, PDF с. 29), и добавляет
  спец-токен DSML с XML-схемой tool-call'ов — `<|DSML|tool_calls>`,
  `<|DSML|invoke ...>`, `<|DSML|parameter ...>` (там же, Table 4, PDF с. 30;
  в прозе OCR написал токен как `|DSML|`, таблица показывает форму
  `<|DSML|...>`).
- **Quick Instruction** (DeepSeek-V4, §5.1.1, Table 5, PDF с. 32):
  выделенные спец-токены (`<|action|>`, `<|title|>`, `<|query|>`,
  `<|authority|>`, `<|domain|>`, `<|extracted_url|>`, `<|read_url|>`),
  дописываемые к входу для вспомогательных задач (решение о веб-поиске,
  генерация заголовка/запросов, классификация домена) с переиспользованием
  KV-кэша. Форматные строки таблицы заодно раскрывают литералы ролей и EOS:
  `<|User|>`, `<|Assistant|>`, `<|end_of_sentence|>`. Обратите внимание на
  разделение труда: эти токены дописывает *сервисный стек* на каждый запрос —
  они не зашиты в каждый документ предобучения. Это чистая версия того, что
  авторы HRM-Text сделали грязнее через condition-токены (§8.0).

### Qwen (Qwen2.5, Qwen3)

- BBPE, 151 643 обычных токена в Qwen2.5; набор control-токенов расширен с
  3 до 22 (два новых — под tool calls), словарь унифицирован по всем
  размерам Qwen2.5 (Qwen2.5, §2 «Architecture & Tokenizer», PDF с. 3).
  BOS/EOS/PAD статья не раскрывает (проверено).
- Qwen3 использует тот же токенизатор, словарь 151 669 (Qwen3, §2, PDF
  с. 3).
- **Нет BOS** (`bos_token: null`, `add_bos_token: false`); eos =
  `<|im_end|>`; pad = `<|endoftext|>`; роли ChatML `<|im_start|>` /
  `<|im_end|>` (HF: tokenizer_config.json Qwen3-32B).
- Мышление/не-мышление — **шаблонного уровня** механизм, обученный на
  стадии Thinking Mode Fusion SFT: флаги `/think` и `/no_think` идут в
  пользовательский запрос (обычный текст, не спец-токены), а в
  не-мыслящих сэмплах в ответе ассистента сохраняется **пустой think-блок**,
  чтобы формат вывода был идентичен в обоих режимах (Qwen3, §4.3, Table 9,
  PDF с. 11). В многоходовых диалогах ответ следует *последнему* встреченному
  флагу (там же). «Thinking budget» прикручен на инференсе: при достижении
  бюджета длины мышления вставляется фиксированная stop-thinking инструкция с
  `</think>`, и модель отвечает по накопленному рассуждению (Qwen3, §4.3,
  PDF с. 11). RL затем закрепляет разделение `<think>`/`</think>` как
  format-following (§4.4, PDF с. 12).
- `<think>`/`</think>` **присутствуют** в таблице added tokens Qwen3 (id
  151667–151668, `special: false`) — проверено на конфиге Qwen3-0.6B
  (экстракция конфига Qwen3-32B обнуляет эти поля — ей не верьте). При этом
  чат-шаблон обращается с ними как с литеральным текстом внутри ответа
  ассистента; `enable_thinking=false` вставляет пустой блок
  `<think>\n\n</think>\n\n` (HF: tokenizer_config.json Qwen3-0.6B).

### Kimi (k1.5, K2; Moonshot)

- В статье k1.5 **нет** никакой информации о токенизаторе и спец-токенах
  (проверено полнотекстово); единственный факт о раскладке токенов — пакинг в
  SFT: «we pack multiple training examples into each single training
  sequence» (Kimi k1.5, §2.5.2, PDF с. 8) — без разделителей и масок.
- Статья K2 документирует только токен-шаблон tool-calling'а (Appendix B,
  PDF с. 26–27): декларация инструментов
  `<|im_begin|>tool DECLARE<|im_middle|>...<|im_end|>`, вызовы внутри
  `<|tool_call_section_begin|>...<|tool_call_section_end|>` с пополневой
  схемой `<|tool_call_begin|>functions.{name}:{counter}<|toolArguments_begin|>{json}<|tool_call_end|>`,
  результаты как `<|im_begin|>tool<|im_middle|>## Results of {call_id}...`;
  constrained-decoding «enforcer» держит генерацию в рамках шаблона.
- Токенизатор семейства tiktoken, словарь ~163.8K; явные `[BOS]` / `[EOS]` /
  `[UNK]` / `[PAD]`; ролевые токены `<|im_user|>`, `<|im_assistant|>`,
  `<|im_system|>`, `<|im_middle|>` (HF: tokenizer_config.json
  Kimi-K2-Instruct — статья ничего из этого не приводит).

### GLM-4.5 (Z.ai)

- Секции про токенизатор в статье нет (проверено), но глава про SFT
  показывает чат-формат: XML-теговый шаблон function-call'ов
  (`<tools>...`, `<tool_call>{name}\n<arg_key>...\n</arg_key><arg_value>...`,
  результаты в `<tool_response>`), мотивированный проблемами экранирования,
  с pipe-стилевыми ролевыми маркерами `<|assistant|>`, `<|observation|>`,
  `<|user|>` и литеральными блоками `<think>...</think>` внутри ходов
  ассистента (GLM-4.5, §3.1, Figure 4, PDF с. 6–7).
- Политика пакинга сформулирована явно: в предобучении best-fit packing не
  используют («random truncation is a good data-augmentation strategy»), в
  mid-training применяют best-fit packing, «чтобы не резать рассуждения и
  repo-level код» (GLM-4.5, §2.3, PDF с. 5). FIM «применяется ко всем
  исходным кодам» (§2.2, PDF с. 4).
- Словарь ~151.3K; eos = pad = `<|endoftext|>`; роли `<|system|>` /
  `<|user|>` / `<|assistant|>` / `<|observation|>`; выделенный спец-токен
  `/nothink` выключает рассуждение; легаси `[MASK]`/`[gMASK]`/`[sMASK]`
  сохранены (HF: tokenizer_config.json GLM-4.5).

### Llama 3 (Meta)

- Словарь 128K: «100K токенов из токенизатора tiktoken плюс 28K
  дополнительных токенов для поддержки неанглийских языков»; компрессия
  выросла с 3.17 до 3.94 символа на токен относительно Llama 2 (Llama 3,
  §3.2, PDF с. 7).
- Маскирование внимания между документами внутри запакованной
  последовательности используется и названо важным в основном для
  continued-pretraining на длинном контексте (§3.2, PDF с. 6).
- Чат-протокол «использует различные специальные header- и
  termination-токены… чтобы обозначать источник и адресата каждого
  сообщения» — их написания статья не печатает (§4.1.1, PDF с. 16). В DPO
  ровно эти форматирующие токены маскируются из loss, потому что обучение на
  них «может приводить к нежелательному поведению вроде хвостовых повторов
  или внезапной генерации termination-токенов» (§4.1.4, PDF с. 16).
- Литералы заполняет HF-конфиг: BPE 128K + 256 зарезервированных слотов
  спец-токенов (id 128000–128255); BOS `<|begin_of_text|>`, EOS
  `<|end_of_text|>`, выделенный pad `<|finetune_right_pad_id|>`;
  структурные токены `<|start_header_id|>` / `<|end_header_id|>` /
  `<|eot_id|>` (HF: tokenizer_config.json Meta-Llama-3.1-8B, зеркало).

### Grok-1 (xAI)

- SentencePiece, словарь 131 072; выпущен как базовая модель, публичного
  чат/спец-токенового оформления нет — в `xai-org/grok-1` вообще нет
  `tokenizer_config.json` (github.com/xai-org/grok-1).

### Поколение середины 2026 (GLM-5.x, Kimi K3, Qwen3-Next)

Конфиги проверены напрямую; смысл подраздела — поменяли ли новые флагманы
конвенции выше. Не поменяли — конвенции ещё сильнее сошлись:

- **GLM-5.2 / GLM-5.3** (Z.ai, август 2026): тот же блок, что у 4.5 —
  eos = pad = `<|endoftext|>`, роли `<|system|>/<|user|>/<|assistant|>/<|observation|>`,
  мультимодальные маркеры `begin/end_of_*`; в 5.3 вернулись `<sop>`/`<eop>`;
  контекст 1M (HF: tokenizer_config.json GLM-5.2 и GLM-5.3).
- **Kimi K3** (Moonshot, август 2026): сохраняет токенизатор семейства
  tiktoken и ядро `[BOS]`/`[EOS]`/`[UNK]`/`[PAD]`, но чат-маркеры переехали
  на header-стиль: `[start_header_id]`/`[end_header_id]` +
  `<|end_of_msg|>` + `[EOT]`, плюс
  `<|media_begin|>/<|media_content|>/<|media_end|>/<|media_pad|>` (HF:
  tokenizer_config.json Kimi-K3).
- **Qwen3-Next** — примечателен тем, что именно на него указывает дефолтный
  путь токенизатора в `main.rs` этого репо: блок id 151643–151668 совпадает
  с Qwen3 (включая vision-токены), пары `<tool_call>`/`<tool_response>`/`<think>`
  — added tokens (special: false), BOS нет, eos = `<|im_end|>` (HF:
  tokenizer_config.json Qwen3-Next-80B-A3B-Instruct).

Вывод: на середину 2026 поле всё так же стоит на одном скелете — один EOS,
завершающий ход ассистента, ролевые разделители в стиле ChatML, think-теги,
выделенный или алиаснутый на EOS pad, — и вендоры в основном
*переименовывают* одну и ту же горсть ролей, а не изобретают новую
структуру. Рецепт §8.1 лежит ровно на этом сошедшемся скелете.

### Кросс-вендорные выводы (и как из них следует §8.1)

1. **BOS**: есть у DeepSeek/Llama/Kimi, нет у Qwen/GLM. Оба дизайна
   доказаны на масштабе; §8.1 включает `<|begin_of_text|>` ради явного
   якоря генерации и будущих не-QA данных.
2. **Один EOS везде же играет роль конца ответа**: DeepSeek завершает EOS
   каждый ход ассистента; у Qwen eos — это и есть закрывающий ход
   `<|im_end|>`. §8.1 оставляет единственный стоп-токен `<|endoftext|>`.
3. **PAD**: отдельный токен паддинга есть только у Llama и Kimi;
   DeepSeek/Qwen/GLM паддят EOS'ом. §8.1 держит `<|PAD|>` отдельно, чтобы
   паддинг нельзя было спутать с настоящим стоп-сигналом в маске loss.
4. **Think-теги**: есть как added tokens в Qwen3 (id 151667–151668) и как
   выделенная пара в DeepSeek-V4 (PDF с. 29); R1-Zero ввёл их как обычные
   текстовые теги шаблона, закреплённые format-наградой (R1, Table 1, PDF
   с. 3). §8.1 делает `<|think|>`/`</think|>` настоящими спец-токенами —
   атомарность гарантирована словарём, а текст корпуса их сминтить не может
   (§8.0).
5. **Aux-токены — паттерн сервисного слоя** (DeepSeek-V4 Quick Instruction,
   Table 5, PDF с. 32): дописываются системой на запрос, а не зашиваются в
   поток предобучения. Именно поэтому condition-токены авторов HRM-Text
   внутри каждой обучающей строки — неправильный слой, и именно поэтому §8.2
   убирает их из потока токенов целиком.
